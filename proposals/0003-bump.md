# 0003: `rvn bump`, raising a dependency across modules

Status: proposed, 2026-10-21
Date: 2026-10-21

## Problem

When a library has a 0-day, the fix is the same everywhere: raise one dependency, in every module that uses it, and prove that it took effect. In a Maven workspace that is a hunt. The version may be a literal in a module POM, a `${property}` in a parent, a `<dependencyManagement>` entry, or an imported BOM; or the library may arrive only transitively, with no declaration to edit. Then every `rayvn.lock` has to be regenerated. People and bots do this by hand or with scripts that do not know the module graph.

The goal is one command that a person or a bot can run, whose result can be reviewed and merged, and which fails loudly if the bump did not take effect.

## Command

```sh
rvn bump <group:artifact> <version> [-f pom.xml] [-m module] [--dry-run] [--json] [--allow-downgrade] [--no-pin-transitive] [--test]
```

| Flag | Meaning |
|---|---|
| `--dry-run` | Compute and report; write nothing. Same output and exit code as a real run. |
| `--json` | Report as JSON on stdout (below). Progress stays on stderr. |
| `--allow-downgrade` | Permit a target lower than a version currently in use. Refused otherwise. |
| `--no-pin-transitive` | Do not add a managed entry for a transitive-only artifact; report it and stop. |
| `--test` | After re-locking, run `rvn test` in the affected modules (the test cache keeps this cheap). |
| `-m module` | Limit to this module and what depends on it. |

`bump` never commits, branches or opens a pull request. The caller's tooling does that.

## Where the edit goes

For each module in scope, find where the version of `<group:artifact>` is decided, and edit that place once. First match wins:

1. **Property.** The dependency (or managed entry) uses `${prop}`: change the property's definition. Several modules reading one property are one edit.
2. **Managed entry.** The version comes from `<dependencyManagement>` in this POM or a parent on disk: change that entry.
3. **Literal.** A `<version>` inside the `<dependency>`: change the literal.
4. **Transitive only.** No module declares it, but it is in a lock. Add a `<dependencyManagement>` entry in the nearest POM on disk that every affected module inherits from (the workspace root if there is no closer one), marked with `<!-- rvn bump: remove when no longer needed -->`. This is on by default, because a bump that does nothing for transitive use defeats the purpose of a 0-day response. The report marks these edits `pin`.
5. **Imported BOM.** The version comes from an `import`-scope BOM. The BOM is not ours to edit, so add an override managed entry as in 4 and report it as `override`, naming the BOM.
6. **Property or parent outside the workspace.** If the deciding POM is not on disk (a parent resolved from a repository), the same override entry is added in the nearest local POM.

Edits are splices into the original text at byte ranges from the parser. Comments, indentation and ordering are untouched, and the XML is never re-serialised, so the diff is the version strings and nothing else.

## After the edit

1. Re-lock every module whose POMs changed and every module that depends on one (the sibling graph from `docs/workspace.md`).
2. **Verify.** In every module whose lock contains `<group:artifact>`, the locked version must now be the target. A module that still resolves another version is a failure; the report names it and the reason when it is known (a different managed pin, an exclusion, a sibling pinning a lower version, `provided` scope mediated lower). Nothing is rolled back; the files are left for inspection, and `git checkout` undoes them.
3. With `--test`, run the tests of the affected modules.

The target must exist in a repository. Resolution fetches it during re-locking; a missing version fails the run before the report says anything changed.

## Safety for automation

- **Idempotent.** Running it again with the same arguments changes nothing and exits 3.
- **No silent downgrade.** A target below any version in use is refused unless `--allow-downgrade`.
- **Exit codes.** 0 changed and verified; 3 nothing to change; 1 failed (including verification). With `--dry-run`, the same codes describe what a real run would do; a dry run cannot verify resolution without writing, so it resolves in a temporary copy and reports the result of that.
- **Deterministic output.** Modules and edits in build order; no timestamps.

`--json`:

```json
{
  "artifact": "org.apache.logging.log4j:log4j-core",
  "target": "2.17.1",
  "changed": true,
  "edits": [
    {"file": "pom.xml", "kind": "property", "name": "log4j.version", "from": "2.14.0", "to": "2.17.1", "modules": ["core", "app"]},
    {"file": "tools/pom.xml", "kind": "pin", "from": null, "to": "2.17.1", "modules": ["tools"]}
  ],
  "modules": [{"name": "app", "locked": "2.17.1", "ok": true}],
  "failures": []
}
```

`kind` is one of `property`, `managed`, `literal`, `pin`, `override`.

## What we leave out

- **Finding what to bump.** `bump` takes the artifact and version from the caller. An `rvn audit` that reads the locks and asks an advisory source (OSV, GitHub) would make that automatic, but it is a call to a third-party service and its own proposal.
- **Choosing the version.** No "latest" or "lowest fixed". A bot or person decides; a minimum-age rule for new releases could live in `audit`.
- **Version ranges.** POMs pin exact versions, so there is nothing to float.
- **Editing imported BOMs and parents outside the workspace.**
- **Committing or opening pull requests.**

## Implementation steps

1. Version locator: for a module and `group:artifact`, report where its version is decided and the byte range to replace (pure functions over parsed POM text; unit-tested on literal, property, managed, inherited, BOM and transitive cases).
2. Splice and the pinned-entry insertion, tested on text with comments, CRLF and odd indentation, and a round trip that changes only the intended bytes.
3. The `bump` command: scope, downgrade check, edits, re-lock, verification, report; `--dry-run` through a temporary copy.
4. `--json`, exit codes, docs (`docs/bump.md`, README, STATUS) and a CI example.
5. Later: `--test`, then `rvn audit`.

## How Gradle, Bazel, uv and Maven handle it (from memory, unchecked)

- **Gradle.** A version catalog (`libs.versions.toml`) or a platform holds each version once, so a bump is one line. A transitive-only fix is a constraint (`constraints { implementation("g:a:2.17.1") }`) or a resolution rule. `dependencyInsight --dependency log4j` shows who pulls it. There is no built-in "bump everywhere" command; Renovate and Dependabot edit the catalog. Lockfiles are regenerated with `--write-locks`.
- **Bazel.** Versions are declared in `maven_install` (WORKSPACE) or `maven.install` (`MODULE.bazel`), and `bazel run @maven//:pin` regenerates the lock. One version per artifact is the rule, so a bump is naturally global. Transitive pins go in `override_targets` or `version_conflict_policy`.
- **uv.** `uv lock --upgrade-package name` re-resolves one package within its constraints, and the workspace has one lock, so it is global. Python specifiers are ranges, so a lock-only bump is possible; Maven's exact pins make a POM edit unavoidable.
- **Maven.** `versions:use-dep-version`, `versions:set-property` and `versions:update-properties` edit POMs, one module or reactor-wide, but they do not touch lock files, add a pin for a transitive library, or check that the result took effect. `dependency:tree -Dincludes=g:a` finds users.

`rvn bump` takes the part they share (edit the declaration, regenerate the lock) and adds what none of them do in one step: handle the transitive-only case, and fail if the locks do not show the target afterwards.
